## Platform detection

`code-review` reviews GitLab merge requests and GitHub pull requests with the same engine, and picks the platform automatically:

1. An explicit `--platform github|gitlab` (or `CODE_REVIEW_PLATFORM`) always wins — an unknown value is an error.
2. Otherwise CI markers decide: `GITHUB_ACTIONS=true` → GitHub; `GITLAB_CI=true` (or a present `CI_PROJECT_ID` / `CI_SERVER_URL`) → GitLab.
3. Failing that, the tool infers from whichever side's required identifiers are present (`GITHUB_REPOSITORY` + a PR number vs. `CI_PROJECT_ID` + `CI_MERGE_REQUEST_IID`). It errors when both sides are present (ambiguous) or neither is (undetectable) — set `--platform` to resolve it.

The GitLab and GitHub identifier/token variables below are read only for the resolved platform; the model, its API key, and the shared knobs apply to both.

### Namespacing provider/infra variables with `CODE_REVIEW_`

In a shared CI environment (GitLab CI, or a GitHub Actions org/repo secret set), the provider credentials and infra variables read by the AI SDK use generic, provider-standard names (`ANTHROPIC_API_KEY`, `OPENROUTER_API_KEY`, `OPENAI_API_KEY`, `OLLAMA_HOST`, ambient AWS/Vertex creds, …). To avoid collisions with unrelated jobs and make it obvious which variables belong to code-review, you can optionally prefix any of them with `CODE_REVIEW_`. At startup, each `CODE_REVIEW_<NAME>` variable is exposed as `<NAME>`:

```
CODE_REVIEW_ANTHROPIC_API_KEY     → ANTHROPIC_API_KEY
CODE_REVIEW_OPENROUTER_API_KEY    → OPENROUTER_API_KEY
CODE_REVIEW_OPENAI_API_KEY        → OPENAI_API_KEY
CODE_REVIEW_OLLAMA_HOST           → OLLAMA_HOST
CODE_REVIEW_GITLAB_TOKEN          → GITLAB_TOKEN
```

This is purely additive — unprefixed variables keep working unchanged. When both `CODE_REVIEW_<NAME>` and a plain `<NAME>` are set, the prefixed value wins, so the tool's scoped value overrides an unrelated CI-wide variable of the same name. The tool's own `CODE_REVIEW_*` settings listed above (e.g. `CODE_REVIEW_MODEL`, `CODE_REVIEW_OTEL`) are reserved and are never de-prefixed.

`--thinking` controls extended thinking on the underlying agent. Thinking tokens are billed at the model's output token rate, so higher levels cost more — the `Review usage:` line and `review-usage.json` reflect that cost.

`--posting-mode draft` is **GitLab-only** (GitHub has no draft-then-publish flow, so the flag has no effect there). It creates GitLab draft notes for every fresh comment and publishes them atomically via `POST /draft_notes/bulk_publish`. The reviewer either appears fully on the MR or not at all, instead of leaking partial state if the job is interrupted. If a draft creation fails mid-flight, the run sweeps the partial drafts before reporting the failure; if the job is killed before that, the next run's orphan cleanup picks them up. Requires a GitLab version that exposes the `draft_notes` and `bulk_publish` endpoints (≥ 15.10) and a token whose user can own draft notes — keep `direct` for older self-hosted instances or restricted tokens. `bulk_publish` publishes _all_ of the current user's drafts on the MR, so use a dedicated bot account if multiple processes may share the token.

## Review-outcome labels

`--labels-on-findings` and `--labels-on-clean` let automation (for example a bot that implements review feedback) react to the outcome of a review. Both are off by default; with neither set, the review makes no label API call.

At the end of a successful review, after the comments are published (including the `--posting-mode draft` bulk publish), the run picks one outcome:

- **findings**: the review posted at least one new comment. Duplicates of existing comments are not reposted, so they do not count.
- **clean**: the review posted no new comment.

The run adds the labels of that outcome and removes the labels of the other outcome, for example `--labels-on-findings mr::change-requested --labels-on-clean mr::needs-review`. The removal is explicit because GitLab CE does not enforce scoped-label exclusivity. A label cannot be in both sets.

- GitLab: one `PUT /projects/:id/merge_requests/:iid` with `add_labels` and `remove_labels`. GitLab creates a missing project label on add.
- GitHub: one `DELETE /repos/:owner/:repo/issues/:number/labels/:name` for each label to remove (a 404 for a label that is not on the PR is ignored), then one `POST .../labels` for the labels to add. The token needs `pull-requests: write` (or `issues: write`), which the review already needs, so the reusable workflow needs no extra permission. GitHub creates a missing repository label on add.

Labels do not change when the review fails, when it is skipped (commit already reviewed, provider out of quota), or under `--dry-run` / `--no-post`, which log the change they would make. A failed label update (for example a token without label permission) logs a warning and does not fail the job, because the review is already published. The applied outcome is exposed as the `code_review.labels.outcome` OTel attribute on the run span.
